Overview #

Three logical surfaces. Pick the one that matches your integration shape:

SurfacePath prefixAuthUse when
External (programmatic) /api/v1/external/* Bearer btz_… You're a separate process or service that needs to provision domains / mailboxes / SSL on behalf of your platform users.
Panel (JWT) /api/v1/{whm,cpanel}/* Bearer JWT from /auth/login You're building or scripting the same surface a human operator uses in the browser. Tenant scoping mirrors the panel.
Inbound webhooks /api/v1/deploy/webhooks/* HMAC-verified per project You're a Git host (GitHub) telling the panel to redeploy on push.

Authentication models #

Bearer JWT — issued by POST /api/v1/auth/login. 4-hour access TTL, 7-day (or 30-day for remember_me) refresh TTL. Pair access + refresh; on a 401 from any endpoint, post the refresh token to /auth/refresh and retry.

Bearer API token — issued by POST /api/v1/whm/developer/tokens (or the cPanel mirror). Format:

btz_prod_a1b2c3d4e5f6_<32-byte hex secret>
└─┬─┘ └─┬─┘ └────┬─────┘ └────────┬───────────┘
 prefix env  public token id     secret half (bcrypt-hashed)
  • The plaintext is shown ONCE on create / rotate. Store it in your secret manager — there is no way to retrieve it again.
  • Scopes are checked per-route. Token scopes can never exceed the issuing user's RBAC permissions.
  • pinned_vendor_id (owner-issued tokens only) immutably scopes every call to that vendor's tenant. vendor_admin tokens cannot set this field.

Response envelope #

Every JSON response uses one of two shapes:

{ "success": true,  "data": { ... }, "error": null }
{ "success": false, "data": null,    "error": {
    "code": "VALIDATION_FAILED",
    "message": "domain is required",
    "fields": { "domain": "must be a valid hostname" }
} }

Paginated list endpoints add a pagination sibling: { page, limit, total, total_pages }.

Rate limits #

External API tokens default to 600 reads/min, 60 writes/min. JWT sessions inherit RATE_LIMIT_WHM / RATE_LIMIT_CPANEL from the server config. A throttled response returns 429 with a Retry-After header (seconds).

POST /api/v1/auth/login #

Sign in with email + password. Returns the JWT pair and the user profile.

POST /api/v1/auth/login
Content-Type: application/json

{ "email": "admin@example.com", "password": "...", "remember_me": false }

200 →

{
  "success": true,
  "data": {
    "access_token":  "eyJhbGciOi...",
    "refresh_token": "abc123…",
    "expires_in":    14400,
    "token_type":    "Bearer",
    "user": { "id": "...", "email": "...", "role": "vendor_owner", ... }
  }
}

POST /api/v1/auth/refresh #

Exchange a refresh token for a new access + refresh pair (refresh tokens are single-use; the response carries the next one).

POST /api/v1/auth/refresh
Content-Type: application/json

{ "refresh_token": "abc123…" }

GET /api/v1/auth/me #

Return the signed-in user's profile (id, username, email, name, role).

GET /api/v1/auth/me
Authorization: Bearer <jwt>

POST /api/v1/auth/forgot-password #

Mail a password-reset link. Returns a generic success regardless of whether the email matches an account — enumeration-resistant by design. The reset link is bound to the requesting browser via an HTTP-only cookie.

POST /api/v1/auth/forgot-password
Content-Type: application/json

{ "email": "user@example.com", "surface": "whm" }

surface is optional and selects which panel the emailed link points at (whm or user-panel). Defaults by user role.

POST /api/v1/auth/reset-password #

Consume a reset token (from the email link) and set a new password.

POST /api/v1/auth/reset-password
Content-Type: application/json

{ "token": "<hex token from URL>", "new_password": "..." }

POST /api/v1/auth/otp/{request,verify,cancel} #

Passwordless email-OTP login. request sets a bz_otp_bind HTTP-only cookie on the requesting browser; verify requires that cookie back, which defeats the "magic URL pasted into another browser" attack. cancel revokes any pending OTP for the originating browser ("Dismiss this session").

External token format #

btz_prod_a1b2c3d4e5f6_aabbccddeeff00112233445566778899aabbccddeeff00112233445566778899
                       ↑                                  ↑
                       │                                  │
                  public token id (visible)        secret half (bcrypt server-side)

Send it as a Bearer token:

Authorization: Bearer btz_prod_a1b2c3d4e5f6_aabbccddeeff…

External — Domains #

GET /api/v1/external/domains

domain:read Paginated list of domains the token can see. Query: page, limit, search.

POST /api/v1/external/domains

domain:write Create a domain.

POST /api/v1/external/domains
Authorization: Bearer btz_…
Content-Type: application/json

{
  "domain":      "example.com",
  "user":        "konsultkaro",
  "php_version": "8.2",
  "environment": "prod",
  "registrar":   "GoDaddy",
  "expires_on":  "2026-12-31"
}

environment is optional — the deployment tier for the new domain/subdomain. One of prod (default), dev, test, local; any other value normalises to prod.

External — Cloudflare #

Connect a domain to the panel's Cloudflare account and read its nameservers — the reseller flow: create the domain, connect it, then hand the customer the Cloudflare nameservers for their registrar. Uses the panel owner's centralized Cloudflare token (WHM → Settings → Cloudflare must be enabled). Every call is per-domain scoped (the token must own {domain}).

GET /api/v1/external/cloudflare/{domain}/nameservers

cloudflare:read The nameservers to give the customer for their registrar. Call this after connecting. 404 until the domain is connected.

GET /api/v1/external/cloudflare/example.com/nameservers
Authorization: Bearer btz_…

→ 200 { "success": true, "data": {
    "domain": "example.com", "status": "pending",
    "nameservers": ["dana.ns.cloudflare.com", "rob.ns.cloudflare.com"] } }

GET /api/v1/external/cloudflare/{domain}

cloudflare:read Zone status. Returns { "connected": false } when the domain has no Cloudflare zone yet, else connected, zone_id, status, nameservers.

POST /api/v1/external/cloudflare/{domain}/connect

cloudflare:write Find-or-create the domain's Cloudflare zone (never duplicates; idempotent) and return the assigned nameservers. Response includes created: true|false. 400 when Cloudflare isn't enabled on the panel.

GET /api/v1/external/cloudflare/{domain}/nameserver-status

cloudflare:read Live delegation check — a real DNS NS lookup vs Cloudflare's assigned nameservers + zone status. Returns connected, cf_nameservers, current_nameservers, delegated, and state (not_connected · nameserver_update_required · pending_activation · active · paused). Since v3.1.195 the panel also auto-refreshes this in the background (~20 min) so a domain flips to active on its own once delegation propagates.

POST /api/v1/external/cloudflare/{domain}/verify

cloudflare:write The "Verify domain" action (v3.1.198). Asks Cloudflare to re-check the zone's nameserver delegation now (activation check) instead of waiting for its periodic scan, then returns the freshly computed status (same shape as nameserver-status). Call after pointing the registrar at the Cloudflare nameservers. Cloudflare rate-limits the underlying check (~1/5 min/zone); the live status is still returned if throttled.

External — Guest links #

POST /api/v1/external/guest-links

guest:create Mint a one-time, browser-locked login URL for a single domain and redirect an end-user to it. The session has no login and shows no other data: 30 minutes from first open, locked to the first browser that opens it. A main domain gets Manage Email + Manage DNS (no zone create/delete, no apex @ A/AAAA); a subdomain gets Manage Email only. The link type is auto-derived from whether the domain is a subdomain of a panel-managed zone.

POST /api/v1/external/guest-links
Authorization: Bearer btz_…
Content-Type: application/json

{
  "domain":                "acme-store.com",
  "max_mailboxes":         5,
  "default_quota_mb":      1024,
  "default_send_per_hour": 200
}

Response (the url is shown only once — redirect the user to it):

{
  "url":        "https://panel.example.com/user-panel/m/gst_prod_ab12cd34_…",
  "link_type":  "email_dns",
  "domain":     "acme-store.com",
  "expires_at": "2026-06-18T12:00:00Z"
}

The three limits are optional (defaults shown). max_mailboxes caps how many mailboxes the guest may create; default_quota_mb and default_send_per_hour are applied to each mailbox the guest creates.

What happens next (you don't call these): the user lands on /user-panel/m/<token>; the page calls POST /api/v1/guest/redeem, which sets HttpOnly cookies (bz_guest_sess + bz_guest_bind), binds the link to that browser, and starts the 30-minute window. The page then drives the cookie-authed guest surface — /api/v1/guest/session, /mailboxes, /mailboxes/{addr}/password, /mailboxes/{addr}/webmail-link, /forwarders, and (main domains only) /dns/records. Every call is hard-scoped to the one domain; apex @ A/AAAA and zone create/delete are blocked. Full list in the OpenAPI spec and Postman collection.

External — Deploy Software #

GET /api/v1/external/deploy/services

deploy:read Flat, paginated inventory of every Deploy Software service the calling token can see — across all projects in the tenant. Each row carries its parent project's project_name, project_slug, and project_user so consumers can render context without a second round-trip per project.

GET /api/v1/external/deploy/services?page=1&limit=50&search=shop
Authorization: Bearer btz_…

→ 200
{
  "success": true,
  "data": [
    {
      "id":              "...",
      "project_id":      "65f0a1b2c3d4e5f601020304",
      "project_name":    "Storefront",
      "project_slug":    "storefront",
      "project_user":    "konsultkaro",
      "name":            "web",
      "role":            "backend",
      "framework":       "nextjs",
      "primary_domain":  "shop.example.com",
      "alias_domains":   ["www.shop.example.com"],
      "git_branch":      "main",
      "port":            3050,
      "status":          "running",
      "systemd_unit":    "sp-proj-storefront-web",
      "last_commit_sha": "a1b2c3d4...",
      "last_deployed_at":"2026-04-28T10:15:30Z"
    }
  ],
  "pagination": { "page": 1, "limit": 50, "total": 12, "total_pages": 1 }
}
  • search matches against the service name OR primary_domain (case-insensitive substring). Empty / omitted returns every service.
  • Tenant scoping mirrors the /projects list — vendors only see services in projects belonging to their own tenant.
  • JWT-driven equivalents for in-panel scripting: GET /api/v1/whm/projects/services (admin, requires deploy.manage) and GET /api/v1/cpanel/projects/services (vendor, auto-tenant-scoped).
Where to find these IDs in the panel. Open Deploy Software on either WHM or the User Panel, click into a project, and expand the API / Developer IDs card above the Activity timeline. It surfaces project_id, project_slug, project_user, the project's webhook URL, and a pre-substituted curl example — each with a one-click copy chip. Each service row also shows an id: a1b2c3… chip next to its name; clicking it copies the full ObjectID to the clipboard. No need to dig through Mongo or scrape the URL bar.

POST /api/v1/external/deploy/projects/{id}/services/{svc}/link-domain

deploy:link Attach a domain to a project service. Vhost is rewired and SSL is re-issued for the new SAN list.

POST /api/v1/external/deploy/projects/65f.../services/web/link-domain
{ "domain": "shop.example.com" }

DELETE /api/v1/external/deploy/projects/{id}/services/{svc}/link-domain/{domain}

deploy:link Detach a domain. The vhost falls back to the project's PHP-FPM placeholder.

Developer — API tokens #

JWT-authenticated CRUD for the API tokens you (or your vendors) issue. Same surface mirrors at /api/v1/cpanel/developer/tokens/* for the User Panel.

GET /api/v1/whm/developer/tokens/scopes

Catalogue of scopes the caller can grant (filtered to RBAC permissions the caller actually has).

GET /api/v1/whm/developer/tokens

List existing tokens (hashed; plaintext is never returned after the create/rotate response).

POST /api/v1/whm/developer/tokens

Plaintext returned EXACTLY ONCE in the response. Store it; there is no recovery path.

POST /api/v1/whm/developer/tokens
{
  "name":             "deploy-bot",
  "scopes":           ["domain:write", "ssl:write"],
  "pinned_vendor_id": "65f0a1b2c3d4e5f601020304",
  "expires_at":       "2027-01-01T00:00:00Z"
}

→ 201
{ "success": true, "data": {
  "id":     "...",
  "prefix": "btz_prod_a1b2",
  "plaintext": "btz_prod_a1b2c3d4e5f601020304_aabbccddeeff..."
}}

POST /api/v1/whm/developer/tokens/{id}/rotate

Rotate the secret half. Old token is immediately invalid; new plaintext is in the response (one-shot).

DELETE /api/v1/whm/developer/tokens/{id}

Revoke a token. All subsequent calls fail 401.

Developer — Webhooks #

Outbound webhooks let your systems react to panel events without polling. Full event catalogue + verification recipe live on the Webhooks page; the management endpoints follow the same shape as tokens.

GET /api/v1/whm/developer/webhooks/events

Catalogue of event keys the panel can fire — { key, label, description, group }. Render this in your UI as the source of truth.

POST /api/v1/whm/developer/webhooks

Signing secret returned ONCE. Use it to verify X-Betazen-Signature on every delivery (see Webhooks page).

POST /api/v1/whm/developer/webhooks
{
  "url": "https://hooks.example.com/betazen",
  "events": ["domain.created", "ssl.issued", "deploy.completed"],
  "description": "Production fanout",
  "active": true
}

→ 201
{ "data": { "id": "...", "signing_secret": "wh_…(64 hex chars)" } }

POST /api/v1/whm/developer/webhooks/{id}/test

Synchronously fire a webhook.test event to your URL. Response includes the receiver's status code + delivery id so you can verify your handler in real time.

GET /api/v1/whm/developer/webhooks/deliveries

Recent delivery attempts: status code, response body excerpt, retry count, error string.

Inbound — GitHub auto-deploy #

Each Deploy Software project exposes a public webhook URL configured per project. GitHub posts here on every push; the handler verifies X-Hub-Signature-256 using the project's webhook_secret (visible in the project's Edit modal) before triggering a deploy of every service whose git_branch matches the push ref.

POST /api/v1/deploy/webhooks/project/<project_id>
X-Hub-Signature-256: sha256=<hmac of body with project webhook_secret>
X-GitHub-Event: push
Content-Type: application/json

{ "ref": "refs/heads/main", "head_commit": { ... }, ... }
The handler returns 200 even on signature failure — deliberately indistinguishable from a deleted endpoint. Failed deliveries surface in the project's "Last webhook" timeline inside the panel.
